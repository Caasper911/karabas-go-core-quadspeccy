# Архитектура QuadSpeccy для Karabas Go

Ядро: до четырёх Pentagon 128, которые работают параллельно на одной плате Karabas Go, Mini или Mini G
(Spartan-6 XC6SLX25, ISE 14.7). Идея взята у
[QuadSpeccy для ReVerSE-U16](https://github.com/mvvproject/ReVerSE-U16/tree/master/u16_quadspeccy),
а код написан заново. Инфраструктуру платы (MCU-линк, OSD, PLL, ЦАП, сборка Makefile) даёт общий
сабмодуль `modules/` (karabas-go-modules) по образцу karabas-go-core-tsconf.

## Клоки

Один PLL от `CLK_50MHZ`, VCO 925 МГц, фаза 0 (как в TS-Conf):

| Клок | Частота | Делитель | Что на нём |
|---|---|---|---|
| `clk_sys` | 84,09 МГц | /11 | контроллер SDRAM (`rtl/sdram/sdram_ctrl.v`) |
| `clk_bus` | 28,03 МГц | /33 | машины, растр, видео, клавиатура, MCU, OSD |
| `clk_8` | 7,97 МГц | /116 | только такт FT812 (`FT_CLK_OUT` у Mini / Mini G, как в TS-Conf) |

`clk_bus = clk_sys / 3`, поэтому каждый фронт `clk_bus` совпадает с фронтом `clk_sys`. Между
доменами ходят toggle-запросы без синхронизаторов. Эти пути покрывает PERIOD, выведенный из
`TS_CLK_50MHZ` (11,9 нс).

## Платы

Всё ядро — модуль `rtl/quadspeccy.v`. Обёртки плат подключают его к выводам (как `kg_osca_system` в
karabas_go_v6z80p): `karabas_go_top.v`, `karabas_mini_top.v`, `karabas_minig_top.v`, у каждой свои `.prj`, `.xst`,
`.ucf` (выводы Mini / Mini G взяты из karabas-go-core-tsconf, блок таймингов во всех трёх одинаковый). `clk_bus` —
выход ядра, поэтому сеть верхнего уровня называется `clk_bus`, как в ucf.

| | Go | Mini | Mini G |
|---|---|---|---|
| видео | VGA-ЦАП (`V_CLK`) | HDMI (`hdmi_out.v`) | HDMI |
| звук | PCM5102 | sigma-delta `AUDIO_L/R` (1/4 шкалы, как TS-Conf) + HDMI | PCM5102 (BCK 3,5 МГц, 55 кГц, как TS-Conf; у Go 7 МГц) + HDMI |
| дисковод / TR-DOS | есть (`ENABLE_FDC` 1) | нет (0) | нет (0) |
| `MCU_SCK` | не на клоковом выводе | не на клоковом выводе | C9, IBUFG + BUFG |
| MCU INT (линия IO1) / IO0 (вход) | `MCU_SPI_IO[0]` / `[1]` | `MCU_IO[1]` / `[0]` | `MCU_IO[1]` / `[0]` |

FT812 у всех плат только для MCU (его SPI). У Mini / Mini G ему всегда нужен такт 8 МГц на `FT_CLK_OUT` (ODDR2 от
`clk_8`); у Mini G `FT_SPI_SCK` берётся до BUFG `MCU_SCK` (BUFG ведёт только клоковые входы). Пункт OSD «FDD» в
`core.json` только для Go (`"boards": ["go"]`).

HDMI (`rtl/video/hdmi_out.v`): пиксельный клок — сам `clk_bus`, DCM (`kg_dcm`, обратная связь CLK0, CLKFX выровнен
с `clk_bus`) даёт ×5 (140 МГц) и его инверсию для сериализаторов `hdmi_tx` (zhdmi из `modules/`). Растр тот же, что
у VGA Go: 896 × 640 тактов, DE — видимая часть 736 × 576 (`de` из `video_out`), синхроимпульсы отрицательные.
`INPUT_REG = 1`: выход OSD комбинационный, `hdmi_tx` регистрирует его перед TMDS-кодерами. Звук 48 кГц
(аккумулятор на `clk_bus`), `dvi_only` из MCU выключает data islands. Режим нестандартный (736 активных, 48,8 Гц),
монитор по HDMI его принимает (проверено на Mini и Mini G).

## MCU: link v2

Ядро говорит с MCU платы по link v2 (karabas-go-firmware `docs/link_v2.md`, в `core.json` `"link": 2`; нужна
прошивка 26111315 или новее, более старая ядро не загрузит). Модуль — `kg_mcu2` из `modules/` на `clk_bus`, ничего
от v1 (`kg_mcu`, `kg_soft_switches`, `img_sdc`, `kg_osd_overlay`) в ядре нет. Пакет на один CS, прерывание `MCU_INT`
(активно 1) на линии IO1 — бывший вывод burst READY; IO0 (бывший burst CS_N) — вход. `MCU_SCK` до 32 МГц, на Mini G
через IBUFG + BUFG, как раньше. Что берёт ядро:

- **SYS:** 32 переключателя OSD (`SW`, раздел «Переключатели OSD»), `DVI_ONLY`, `BUSY` (MCU настраивает ядро: машины
  в сбросе), кнопки платы `BTNS` 1..0, FT812 (`FT_*`; SD2 не используется, карта №2 у машин).
- **HID:** отчёт клавиатуры целиком по `KBD_WR` (модификаторы и 6 кодов — прежние `kb_status`, `kb_dat0..5` у
  `zx_kbd`), мышь (`MS_WR` — такт на отчёт), джойстики (16 бит, берутся 12..0).
- **LOAD:** ROM из `core.json` (`LD_KIND` 0), раздел «Загрузчик ROM»; с управлением потоком (`LD_READY`, caps бит 4).
- **IMG:** монтировщик образов (`kg_l2_img`, сторона `sdc_*` бывшего `img_sdc`), слоты 0..3 — карты машин.
- **OSD:** битмап 256 × 128 (`kg_l2_osd_overlay`, раздел «Видео»), меню рисует MCU.

## Процессор: один tv80 на четыре машины

Процессор — tv80 (Verilog, `src/rtl/tv80`, из karabas_go_v6z80p, с его исправлениями флагов X/Y для CPI/CPD), один
на все четыре машины (`tv80_quad.v`, `pentagon` `CPU = 2`):

- `tv80q_core.v` генерирует `tools/mkquad.py` из `tv80_core.v`: логика (mcode, ALU, всё комбинационное) одна, каждый
  из 48 регистров состояния — память на 4 записи (`X_m[th]`), регистровый файл — `tv80q_reg` (32 записи). В такте
  обрабатывается CPU `th`: его состояние читается и пишется. Оригинальный `tv80_core.v` не меняется.
- Восемь тактов `clk_bus` на T-состояние: слот `2k` — `cen` CPU машины *k*, слот `2k+1` — «просмотр»: логика уже
  показывает новое состояние CPU *k*, его выходы идут машине прямо в этом такте и держатся до следующего
  просмотра. Машина видит обычный tv80, чей `cen` в слоте `2k` (`cslot` в top, выровнен по `ce_cpu`); входы (данные,
  WAIT, INT, NMI, сброс) берутся в слоте `2k`. Машины сдвинуты друг относительно друга на 2 такта `clk_bus`, и
  растр каждой машины (`ce7`, `hc`, `vc`, INT, кадр) задержан на те же `2k` тактов (`raster_delay.v`): процессор,
  прерывание, выборка видео и бордюр у всех машин в одном соотношении (без этого в Rage у машин 2..4 мультиколор
  и бордюр сдвигались до 4 пикселей). Полноэкранный строчный буфер пишется по растру выбранной машины.
- Проверка: `src/sim/tb_tv80q.v` (`run_tv80q.sh`) — четыре обычных `tv80_core` против `tv80_quad` такт в такт на
  случайных программах (каждый 8-й байт ED, без HALT), со случайными WAIT / INT / NMI / паузами / сбросами, все выходы
  каждого CPU в каждом такте; перебор мутаций (каждый регистр читается из контекста 0) показывает, что тест их
  ловит. `tb_pentagon` с `QUAD=1` — машина на `tv80_quad`.
- T80 (VHDL, версия 351) и одиночный tv80 остаются: `CPU = 0` / `1` у `pentagon`.

Тактовые сигналы Pentagon делаются из `clk_bus` разрешениями (`rtl/zx/zx_timing.v`): `ce7`
даёт 7 МГц (пиксель), `ce_cpu` даёт 3,5 МГц (такт Z80, каждый второй `ce7`). Частота 28,03 МГц
вместо 28,00 даёт CPU 3,504 МГц (+0,1 %).

## Растр Pentagon (общий для всех машин)

Все машины работают синхронно от одного `zx_timing`.

- Строка: 448 пикселей (224 T). `hc` 0..255 занимает paper, 256..319 правый бордюр, 320..383
  гашение (sync), 384..447 левый бордюр.
- Кадр: 320 строк, всего 71680 T. `vc` 0..191 занимает paper, 192..239 нижний бордюр, 240..255
  гашение, 256..319 верхний бордюр.
- INT: 32 T, начинается со строки 239, пикселя 312 (T 156). До первого пикселя paper проходит
  80·224 + 68 = 17988 T, как у Pentagon.
- Flash: бит 4 счётчика кадров.

## SDRAM: банк на машину

Машина *i* живёт в банке *i* SDRAM (8 МБ на банк при 4M×16×4). Контроллер обслуживает банки по
кругу, раунд длится 16 тактов `clk_sys`, у банка *i* окно 4i..4i+3:

```
такт  0  ACT b0            4  ACT b1            8  ACT b2           12  ACT b3
      2  READ b0 (AP)      6  READ b1           10 READ b2          14 READ b3
      3  WRITE b0 (AP)     7  WRITE b1          11 WRITE b2         15 WRITE b3
      5  данные b0 (спад)  9  данные b1         13 данные b2         1  данные b3
```

- В окне выполняется одна операция: чтение или запись одного байта (слово 16 бит + DQM),
  с auto precharge. tRCD = 2 такта, CAS latency 2, SDRAM тактируется инвертированным клоком
  через ODDR2, данные чтения захватываются по спаду клока. Эта временная схема проверена на
  этой плате: так работает SDRAM General Sound в ядре TS-Conf.
- ACT в один и тот же банк повторяется раз в 16 тактов (tRC ≤ 6). ACT разных банков разнесены
  на 4 такта (tRRD). Запись выставляет DQ не раньше чем через такт после того, как ушли данные
  чтения соседнего банка.
- Refresh: каждый 32-й раунд проходит без обращений, на такте 6 в нём идёт AUTO REFRESH.
  Получается раз в 6,1 мкс (норма 7,8 мкс).
- У банка два канала. **A**: CPU, а пока машины в сбросе, загрузчик ROM. **B**: видео.
  В начале окна A имеет приоритет над B.
- Каждая машина получает 84,09 / 16 = 5,26 млн обращений/с. Pentagon в среднем расходует
  ≈ 0,84 обращения на T (CPU ≤ 1/3, видео 1/2), то есть ≈ 2,9 млн/с.

### Бюджет задержки чтения CPU

T80 (обёртка в `pentagon.v` повторяет T80se) берёт данные на фронте `ce_cpu`, который
заканчивает T2. Запрос в SDRAM уходит в начале T1, а не по RD_n, по состоянию
T80 (`MC`, `TS`, `Write`, `NoRead`, `IORQ`). Бюджет: 2 T = 48 тактов `clk_sys`.

Порты контроллера (запросы и ответы) — регистры на `clk_bus` у самого контроллера: длинные пути через кристалл к
четырём машинам и от загрузчика получают период `clk_bus` (35,7 нс), а не `clk_sys` (11,9 нс); с 4 машинами на
94 % слайсов прямые пути сходились с запасом 0,03 нс. Это стоит такт `clk_bus` в каждую сторону; машина отдаёт
запрос прямо на такте декодирования T1 (не через `pend`, если канал свободен), запись подтверждается, когда её
окно её взяло (ACT), а не на WRITE. Запас (тестбенч меряет его в тактах `clk_bus` от ответа до такта CPU, который
берёт данные): обычно 9, при совпадении с раундом регенерации 3 (128 ROM, ESXDOS) и 1 (LDIR, `im2test`); меньше
нуля — это WAIT и `late`. Если данные всё же опоздали, `WAIT_n` вставляет такты
ожидания (флаг `late` в `pentagon.v`; на железе такого быть не должно).

Запись CPU уходит в начале T2: `DO` валиден с конца T1. Следующее чтение ждёт окончания записи,
и бюджет всё равно соблюдается (разбор в `pentagon.v`).

### Карта памяти машины (байтовый адрес в банке)

| Адрес | Что |
|---|---|
| `0x00000..0x1FFFF` | RAM, страницы 0..7 по 16 КБ |
| `0x20000` | ROM 0: редактор 128 |
| `0x24000` | ROM 1: 48 BASIC |
| `0x28000` | ROM 2: TR-DOS 5.04T (`roms/trdos504tprofiD.rom`) |
| `0x2C000` | ROM 3: ESXDOS (8 КБ) для DivMMC |
| `0x80000..0xFFFFF` | RAM DivMMC, 64 банка по 8 КБ |
| `0x120000..0x1FFFFF` | RAM, страницы 8..63 (страница p по адресу `0x100000 + p * 16 КБ`) |

Цикл подтверждения прерывания (M1 при `IntCycle_n` = 0) даёт на шину `FF` (как подтяжки Pentagon): в IM 2
младший байт вектора — `FF`. Только в этом M1: дальше (запись PC в стек, чтение вектора из таблицы) идут обычные
обращения к памяти, хотя `IntCycle_n` T80 остаётся низким до конца ответа на прерывание.

Порт `#FE` (бордюр, MIC, beeper) сбросом машины не очищается, как у ULA: бордюр остаётся, пока его не
выставит ROM. `#7FFD` при сбросе обнуляется.

### 1024 КБ RAM (Profi)

Включается для каждой машины в OSD: Memory size 128K / 1024K (soft switch 24 + n, по умолчанию 128K). При 128K
`#DFFD` не декодируется, старшие биты страницы равны 0, порты AY декодируются как у Pentagon (A15 = 1, A1 = 0).
Переключение действует сразу, без сброса.

Как в karabas-go-core-profi, только расширение страниц: порт `#DFFD` (полный адрес), биты 2..0 — старшие биты
страницы в `C000` (страница = `#DFFD` 2..0 и `#7FFD` 2..0, 64 по 16 КБ). Остальные биты (SCO, WOROM, CPM, SCR, DS80
Profi) игнорируются. Сброс обнуляет `#DFFD`.

Экран по-прежнему страница 5 / 7 (`#7FFD` бит 3). Порты AY декодируются с A13 = 1 (`#FFFD` / `#BFFD`), иначе
`#DFFD` попадал бы в выбор регистра AY. Страницы 0..7 лежат там же, где раньше. Проверка: `run_sim.sh` с
`MEMTEST=1` (`src/sim/memtest.asm` вместо ROM 0, DivMMC выключен): метки во всех 64 страницах (старшие биты
`#DFFD` пишутся единицами). Модель SDRAM в тестбенче — 2 МБ на банк (2048 строк).

Порт `#7FFD` (Pentagon: A15 = 0, A1 = 0): биты 2..0 задают страницу в `C000`, бит 3 экран
(страница 7 / 5), бит 4 ROM, бит 5 блокировку. Порт `#FE` (A0 = 0): запись бордюр / MIC / beeper,
чтение клавиатура / tape. Порт `#1F`: Kempston. Kempston mouse (младший байт `#DF`): `#FADF` кнопки (A8 = 0,
`{колесо, 1, кнопки активны нулём}`), `#FBDF` X, `#FFDF` Y (A10).

### Загрузчик ROM

MCU грузит ROM-файлы из `core.json` по адресу загрузчика: биты 17..16 задают номер машины,
биты 15..0 смещение в её ROM-области. Например, машина 2, ROM 1 = `0x24000`. Байты (`LD_*` у `kg_mcu2`, `LD_KIND`
0) идут через FIFO (`kg_fifo`, 1024 слова, 2 RAMB16) в канал A банка. MCU шлёт пакеты DATA по 512 байт (байт не
чаще 250 нс) и перед каждым спрашивает LOAD STATUS: `LD_READY` = в FIFO свободно не меньше 512 слов (caps бит 4).
Байт, всё же заставший FIFO полным, теряется; это отмечает флаг `ld_ovf`, при нём 2-й диагностический квадратик
красный. В link v1 управления потоком не было: FIFO на 256 слов; с 16 словами после этапа 0 оптимизации (порты
контроллера на `clk_bus`, цикл записи на байт длиннее) ломался последний файл, ESXDOS машины 4. Пока загрузчик
работает (`ld_hold`: LOAD ROM, `BUSY` MCU, FIFO не пуст), все машины
держатся в сбросе. Канал A делится XOR-ом toggle-сигналов CPU и загрузчика: активна всегда
только одна сторона.

### Очистка ОЗУ DivMMC

При старте ядра и при Reset All (Win+F12, кнопка платы) первые 128 КБ ОЗУ DivMMC всех машин (банки 0..15,
`0x80000..0x9FFFF` банка SDRAM машины) заполняются нулями. Очистка идёт через загрузчик (`clr_act` в top): один
адрес сразу во все банки (toggle `ld_req` всех машин), 128К шагов по циклу записи — около 50 мс. FIFO загрузчика
идёт первым (ROM при старте), очистка — когда он пуст. Пока она идёт, `ld_hold`: машины в сбросе, состояние
DivMMC (`#E3`, MAPRAM, automap) очищено (`areset` машины), как при включении. Диагностические квадратики
отладки скрыты (`diag_en` = 0).

## Видео

### Полный экран (milestone 1)

Видеовыборка машины (`pentagon.v`) читает байт пикселей и атрибут знакоместа через канал B не
раньше чем за 12 пикселей до показа, в буфер на два знакоместа. Мультиколор работает с точностью
примерно до знакоместа (у настоящего Pentagon выборка идёт во время показа предыдущего
знакоместа).

`video_out.v` работает как scan doubler: нативная строка (448 px, 64 мкс) пишется в один из двух
строчных буферов, предыдущая строка читается дважды на 14 МГц. Выходит 896 × 640 тактов
28 МГц, 31,25 кГц, 48,8 Гц (растр 50 Гц VGA-режима TS-Conf).

Гашение — как у 720 × 576p50: видимая часть 736 тактов × 576 строк (бордюр 56 + 256 + 56 пикселей,
48 + 192 + 48 строк Спектрума). По горизонтали front porch 16 тактов (0,57 мкс), hsync 64 (2,3 мкс), back porch 80
(2,9 мкс); по вертикали 4 + 4 + 56 строк VGA. Раньше видимая часть была 768 × 608 с back porch 16 тактов (0,57 мкс):
мониторы, которые берут уровень чёрного в начале back porch, захватывали там цвет бордюра, и картинка
засвечивалась (найдено на мониторах). Строки гашения считаются по строкам картинки (`sy`, от левого бордюра на
`vga_x` 392), одинаково для полного экрана и quad: по `dl`, который меняется на `vga_x` 0, у первой видимой строки
не было левого бордюра, а у строки после последней он был.

OSD — битмап link v2 (`kg_l2_osd_overlay`): сам меряет область `de` (736 × 576), выбирает масштаб 2 (512 × 256) и
ставит меню посередине; синхроимпульсы берёт активными единицей (в ядре они нулём, инвертируются на входе и
выходе), картинку, синхроимпульсы и `de` задерживает на 2 такта вместе. В link v1 был текстовый `kg_osd_overlay` со
смещениями 96 / 68. На Go выход идёт на VGA-ЦАП платы (`V_CLK` из `bus_ce`), FT812 отключён
(`FT_OE_N` = 1), им пользуется только MCU; на Mini / Mini G — на HDMI (раздел «Платы»).

### Quad-режим

Включается после старта ядра; Win+`~ переключает на выбранную машину во весь экран и обратно.

Видимая часть VGA-растра — 736 тактов × 576 строк — делится на четыре квадранта по 368 × 288.
Это видимая картинка полного экрана (56 + 256 + 56 пикселей, 48 + 192 + 48 строк) при
одном пикселе Спектрума на такт 28 МГц и одной VGA-строке на строку: вдвое меньше полного экрана
по обеим осям. Машина = 2 × ряд + столбец.

- **Строки paper.** Компоновщик (`video_out.v`) в начале каждой строки картинки (`vga_p` = 784)
  запрашивает следующую строку у машин её ряда (`q_go`). Машина в quad-режиме останавливает
  выборку по своему растру и читает 32 × {пиксели, атрибут} через канал B в строчный буфер
  2 × 32 × 16 бит (`pentagon.v`, блочная память RAMB8). Это 64 обращения за VGA-строку (32 мкс). Компоновщик
  выставляет адрес в момент показа, слово приходит на следующем такте (выходной регистр BRAM стоит на месте
  бывшего регистра `qa_word` конвейера), машина выбирается по `qm` этого же такта (`qa_m`).
- **Бордюр.** Машина запоминает цвет бордюра каждой своей строки (на `hc` = 128) в памяти
  512 × 3 бита (RAMB8, чтение как у строчного буфера). Квадрант показывает бордюр по строкам, полосы загрузки
  видны.
- **Сброс машины выборку не останавливает** (как ULA показывает память во время сброса): раньше выборка
  стояла, и квадрант на время сброса (при Reset All с очисткой DivMMC — около 50 мс) показывал последнюю выбранную
  строку по всему экрану — полосы (найдено на плате).
- **Ограничения.** Картинка соответствует экранной памяти в момент выборки, а не лучу машины:
  мультиколор и бордюрные эффекты в quad-режиме неточные. Полноэкранный режим остаётся точным.
- **Бордюр широкий** (paper занимает 46 % площади квадранта). Масштаб 4/3 с пикселями 21 МГц (вариант B
  [QUAD_SCALE.md](QUAD_SCALE.md)) был сделан и проверен на плате, но выглядел плохо и убран.
- Выбранная машина обведена рамкой в 2 пикселя (цвет из OSD, по умолчанию зелёный), несобранные машины (`NUM_MACHINES`)
  показаны серым.
- Координаты: `ld = vga_l − 2` (удвоенная строка, которую показывает и полноэкранный режим),
  строка картинки начинается на `vga_p` = 784 (после back porch), `sy = row − 544` (первая видимая строка
  верхнего бордюра, `dl` 272).
- Проверка: `src/sim/run_vpx.sh` (`tb_vpx.v`: `zx_timing`, `video_out`, модель машин, заполняющих буфер через 400
  тактов после `q_go`) — каждый пиксель quad-кадра против ожидаемого и чёрное вне картинки; в полноэкранном
  режиме 576 строк по 736 пикселей; строка 896 тактов, картинка через 80 тактов после hsync.

## TR-DOS и дисковод (только Karabas Go)

На Go есть разъём дисковода. Один контроллер — `hrdy_fdc` (обвязка Beta Disk) с моделью 1818ВГ93 `vg93_top` и
сепаратором `fdd_glue`, взятые из ядра TS-Conf для Go (`rtl/vg93/`, автор модели — demyanenko-d по реверсу
deathsoft / titus, см. `rtl/vg93/README.md`); работает на `clk_bus`, CLK модели 1 МГц.

- **Какая машина.** Пункт OSD «FDD» (общий, Core 1..4): контроллер и TR-DOS у этой машины, если у неё выключен
  DivMMC (оба перехватывают 3D00..3DFF). У остальных машин TR-DOS нет. Контроллер сбрасывается вместе с машиной
  и держится в сбросе, пока у неё нет TR-DOS.
- **TR-DOS как у Pentagon** (`pentagon.v`, `dos`): включается при выборке опкода из 3D00..3DFF, когда включено
  ПЗУ BASIC 48 (`#7FFD` бит 4), выключается при выборке опкода из ОЗУ (4000..FFFF); сам опкод по 3Dxx читается уже
  из ПЗУ TR-DOS (`dos_instant`, там шрифт BASIC 48). Пока TR-DOS включён, в 0000..3FFF ПЗУ TR-DOS (ROM 2) и видны
  порты контроллера: регистры ВГ93 `#1F` / `#3F` / `#5F` / `#7F` (A7 = 0, A4..A0 = 11111; `#1F` вместо Kempston)
  и системный порт `#FF` (запись: привод, `/MR`, HLT, сторона; чтение: INTRQ, DRQ).
- **Шина.** В `hrdy_fdc` идут адрес и данные процессора этой машины (`q_a`, `q_do` от `tv80_quad`), чтение / запись
  ввода-вывода и выборки портов от машины, `ena_cpu` — её слот процессора (`ce_m`). WAIT контроллера (`busy`:
  выдерживает время между обращениями как у 3,5 МГц и после записи в регистр) идёт в `cpu_wait_n` машины.
  Стробы и выборки — с T2, как `/RD` `/WR` у Z80 (`iordwr` у TS-Conf): данные процессора верны с T2, а `hrdy_fdc`
  пишет порт `#FF` на каждом такте записи; со стробом с T1 туда попадал прежний байт шины, и ВГ93 сбрасывался
  через `/MR`. Запись кончается в начале T3 (только T2 и TW): регистр записи модель выбирает по адресу, взятому в
  конце `/WE` (`vg93_host_bus`), а адрес процессора меняется в такте конца M-цикла; с `/WE` до конца цикла байт
  уходил в регистр следующего адреса или терялся (TR-DOS: NO DISK, найдено на плате; у Z80 `/WR` кончается в
  середине T3). INTRQ / DRQ для чтения `#FF` даёт сам `hrdy_fdc` (`dout`), выходы `intrq_o` / `drq_o` не нужны.
- **Выводы дисковода** как у TS-Conf для Go: активны единицей (`FDC_DRIVE`, `FDC_MOTOR`, `FDC_STEP`, `FDC_DIR`,
  `FDC_WGATE`, `FDC_WDATA`), сторона — `FDC_SIDE_N`. Раньше незанятые выводы стояли в 1 (оба привода выбраны,
  мотор включён); без контроллера теперь 0, `FDC_SIDE_N` = 1.
- **Только Go.** Параметр `ENABLE_FDC` у `quadspeccy` (1 в `karabas_go_top`); на Mini / Mini G (у них нет дисковода)
  он 0: контроллер не собирается, у машин нет TR-DOS (ПЗУ TR-DOS грузится, но не включается).
- Проверка: `run_sim.sh` с `TRDOS=1` (`trtest.asm`): вход в TR-DOS по CALL 3D00 с ПЗУ 48, порт `#1F` и ПЗУ TR-DOS
  внутри, Kempston и ПЗУ 48 после возврата в ОЗУ; на каждом такте записи в `#FF` на шине её байт; с `QUAD=1` и
  `hrdy_fdc` + моделью дисковода в тестбенче — RESTORE (привод готов, головка загружена, дорожка 0) и две записи в
  регистры подряд (сектор, дорожка) с WAIT.

## DivMMC и SD-карты

У каждой машины свой DivMMC (`pentagon.v`), включается в OSD на странице машины.

- **Порты.** `#E3`: 7 CONMEM, 6 MAPRAM (сбрасывается только выключением DivMMC / питанием),
  5..0 банк RAM в `2000-3FFF`. `#E7`: бит 0 — CS карты. `#EB`: SPI. Запись отправляет байт,
  чтение возвращает байт предыдущего обмена и отправляет FF.
- **Отображение.** При CONMEM или automap: `0000-1FFF` ESXDOS ROM (с MAPRAM — банк 3 RAM, только
  чтение), `2000-3FFF` банк RAM (только чтение при MAPRAM и банке 3).
- **Automap** (как в `divmmc.vhd` divgmx, MVV). Выборка опкода по `0000`, `0008`, `0038`, `0066`,
  `04C6`, `0562` ставит `detect`, по `1FF8-1FFF` снимает его, по `3D00-3DFF` (при любом ROM)
  включает отображение сразу, для этой же выборки. Вне выборки `automap` следует за `detect`.
- **Сброс.** Сброс машины не трогает DivMMC: `#E3`, CS карты, `automap`, `detect` очищаются только
  при включении (старт ядра, загрузка ROM: `areset`) и при выключении DivMMC в OSD; `#E3` и CS ещё
  при сбросе с зажатым NMI. Очистка на каждом сбросе давала на плате бесконечную перезагрузку
  ESXDOS 0.8.9.
- **SPI-мастер.** 7 МГц: 4 такта `clk_bus` на бит, режим 0, байт за 32 такта. `IN (#EB)` возвращает
  байт **предыдущего** обмена (он фиксируется в момент запуска нового). Процессор ждёт (WAIT) только
  до запуска своего обмена: пока идёт предыдущий или пока эмулируемая карта ждёт MCU. Если ждать
  и собственный обмен (на автоматическом такте TW цикла ввода-вывода), `IN` возвращает уже новый
  байт, ответы карты сдвигаются на байт и карта не определяется. Так было на плате до исправления.
- **Z-Controller** (всегда включён, и при DivMMC Off: например, у машины с TR-DOS). Тот же SPI-мастер и тот же
  CS. `#57` — как `#EB` (запись отправляет байт, чтение возвращает байт предыдущего обмена и отправляет FF).
  Запись `#77`: бит 1 — CS карты (0 — выбрана), бит 0 (питание карты) не используется. Чтение `#77` даёт `FC`:
  карта вставлена, без защиты записи. Порты по A7..A0, как в karabas-go-core-profi. CS (`#E7` бит 0 или `#77`
  бит 1) и SPI-мастер больше не очищаются при выключении DivMMC: CS сбрасывается при включении (`areset`) и при
  сбросе с NMI, обмен — сбросом машины.
- **Куда идёт SPI** (DivMMC и Z-Controller). OSD «SD card» каждой машины (действует при любом DivMMC):
  - *Image* — `kg_sd_emu` этой машины (из karabas_go_v6z80p: логика карты `nextor_sd.v` ядра MSX,
    SDHC размером с образ, Ncr = 2, выход `waiting`; параметр `CACHE` добавлен здесь, стоит 0: без кеша
    секторов, один буфер на сектор — с кешем 4 × 16 КБ не хватало места), секторы через
    монтировщик образов `kg_mcu2` (сторона `sdc_*`): слот образа *n* = машина *n*, один запрос за раз, младший слот
    первым;
  - *Real* — карта №2 платы (`SD_*`; карта №1 у MCU). Владеет одна машина: младшая с Real (DivMMC
    не важен). У остальных с Real карты нет (MISO = 1).
- **NMI** (F11) подаётся выбранной машине: меню ESXDOS через automap по `0066`.

## Клавиатура и горячие клавиши

`rtl/hid/zx_kbd.v` переводит HID-отчёт MCU (модификаторы + 6 кодов) в матрицу 8×5 и Kempston
(раскладка как у hid_parser profi / tsconf в режиме Spectrum, без макросов).

| Клавиши | Действие |
|---|---|
| Win + 1..4 | клавиатура и джойстики к машине 1..4 |
| Win + стрелки | соседняя машина по квадрантам 2 × 2: влево / вправо — бит 0 `sel`, вверх / вниз — бит 1, без перехода через край; и в полном экране |
| Win + `~ | quad (после старта) / выбранная машина во весь экран |
| F12 (OSD Reset) | сброс выбранной машины |
| Win+F12 (OSD Reset All) | сброс всех машин, очистка ОЗУ DivMMC |
| F11 (OSD NMI) | NMI выбранной машины |

Пока Win нажата, клавиши в машину не идут. Пункт OSD «Keys to» (общий): Selected — клавиатура и джойстики идут в
выбранную машину; All — в quad-режиме во все машины сразу (в полноэкранном режиме всё равно только в выбранную). Звук (beeper / MIC / AY) берётся у выбранной машины.

## Мышь

`rtl/hid/quad_mouse.v`, USB-мышь от MCU (`MS_X` / `MS_Y` / `MS_Z` — приращения, `MS_B`, `MS_WR` — такт на каждый
отчёт; колесо Kempston 4 бита — младшие биты `MS_Z`; HID: x вправо, y вниз, бит 0 кнопок — левая):
- **Полный экран:** Kempston mouse выбранной машины. У каждой машины своя позиция (x, y, колесо, как `kg_cursor` /
  TS-Conf: старт 7F / 7F / 7, y вверх), она двигается, только пока машина на экране, поэтому при возврате к машине
  указатель не прыгает. Кнопки видит только показываемая машина.
- **Quad-режим:** мышь в машины не идёт, у ядра свой курсор — стрелка 16 × 16 (чёрный контур, белая заливка,
  `cursor_row` в `video_out.v`) поверх картинки, горячая точка — левый верхний пиксель, позиция ограничена
  картинкой 736 × 576, старт в центре. Нажатие левой кнопки выбирает машину квадранта под курсором (как Win+1..4,
  `sel_we` в `zx_kbd`; несобранные машины не выбираются). Курсор гаснет через 5 с без отчётов мыши — 244 кадровых
  синхроимпульса VGA (`video_vs`); любой отчёт его показывает. До первого отчёта курсор не виден.
- **Двойной щелчок** левой кнопкой в quad-режиме (второе нажатие в том же квадранте не позже 20 кадровых
  синхроимпульсов, ~0,4 с, после первого) — машина на весь экран (`full_set`).
- **Средняя кнопка** в полноэкранном режиме возвращает в quad (`quad_set`), машины среднюю кнопку не видят.
  Пункт OSD «Mouse middle» (Quad view / Machine) убран: на плате не работал; soft switch 22 не используется,
  `mid_quad` в top = 1.
- Проверка: `src/sim/run_mouse.sh` (`tb_mouse.v`: движение и ограничение, выбор щелчком, позиции машин, кнопки,
  двойной щелчок — быстрый, медленный, в разных квадрантах, средняя кнопка в обоих режимах OSD, гашение через 244
  импульса); курсор в картинке — `tb_vpx.v`.

## Звук: beeper и TurboSound

В каждой машине TurboSound из двух AY (только AY: 16 уровней громкости, огибающая из 16 шагов, YM нет).
Порты как у Pentagon / NedoPC: `#FFFD` (A15 = 1, A14 = 1, A1 = 0) — выбор регистра, а запись `F8..FF` выбирает чип
по биту 0 (`FF` — первый, `FE` — второй); `#BFFD` (A14 = 0) — запись данных. Выбор регистра с ненулевыми битами
7..4 отключает чип до следующего выбора (чтение `FF`, запись не идёт).

У каждой машины только копии её 32 регистров (`pentagon.v`, распределённая RAM 32×8, хранятся только биты, которые
есть у AY, остальные читаются нулями); чтение `#FFFD` идёт из копий. Сброс машины обнуляет её регистры (32 такта, как
RESET у AY), выбор чипа — первый.

Генератор один на все восемь AY (`rtl/sound/turbosound.v`, логика `ay_psg.v`): он обходит голоса по очереди, голос
v = {машина, чип}. Кадр 256 тактов `clk_bus`, на голос 32 такта (шаги 0..19 заняты). Регистры генератор не хранит: он
выставляет `ay_ra` = {чип, регистр} и читает этот регистр у всех четырёх машин сразу (асинхронное чтение копий в
том же такте), берёт данные своей машины. Состояние (счётчики и выходы тонов, LFSR и счётчик шума, счётчик, шаг,
чётность и удержание огибающей) — в распределённой RAM по голосам. Шаги: 0..11 два тика тонов A, B, C (чётный
шаг — младший байт периода, нечётный — старший и тик), 12 шум (R6), 13..15 огибающая (R11, R12, R13), 16 R7,
17..19 уровни A, B, C (R8..R10) в смесь. Запись R13 (по `ay_we` машины) перезапускает огибающую голоса на его
следующем шаге огибающей (до 9 мкс позже, чем у чипа).

Такт AY 1,75 МГц = `clk_bus` / 16: тики тонов раз в 128 тактов (два за кадр), шум (LFSR 17 бит, отводы 0 и 3) и
огибающая раз в 256; счётчики считают вверх, период 0 как 1 (как ym2149.v MikeJ / Sorgelig). Уровни AY — пары
таблицы ym2149.v. Выход — сумма кадра, около 110 кГц.

Какие машины слышны: выбранная и те, у которых в OSD на их странице Sound = Always (переключатели 28..31, по
умолчанию Selected). Смесь (OSD «AY mix» на странице машины, у каждой своя): ABC — левый 2A + B, правый 2C + B;
ACB — левый 2A + C, правый 2B + C; голоса слышных машин складываются (13 бит), ×8 (одна машина звучит как раньше),
плюс у каждой слышной машины beeper `0x2000`, MIC `0x800`, вход магнитофона `0x400`; сумма ограничивается `0x7FFF`
→ выходы ядра `audio_l` / `audio_r`: на Go и Mini G `kg_pcm5102`, на Mini sigma-delta, на Mini / Mini G ещё и HDMI.
Вывод `BEEPER` Go — beeper выбранной машины.

Проверка: `src/sim/run_ts.sh` (`tb_ts.v`: смесь чипов и машин, слышимость, ABC / ACB, тон и огибающая против
`ay_psg`; `NETLIST=1` — смесь на нетлисте XST); `run_sim.sh TESTROM=tstest` — выбор чипов `FF` / `FE` через
`#FFFD`, записи и чтение обоих чипов машиной. Раньше генераторов было два, для выбранной машины, с перезагрузкой
регистров при смене выбора (два `ay_psg` — около 670 LUT).

## Магнитофон

Два общих пункта OSD:
- **Tape in** — Board: вход магнитофона (бит 6 порта `#FE`) всех машин — `TAPE_IN` платы; Core: все машины, кроме
  выбранной в «Tape out», слышат её MIC (бит 3 `#FE`), то есть SAVE в ней — это LOAD в остальных; сама она
  слышит `TAPE_IN`.
- **Tape out** — Core 1..4: MIC этой машины идёт на `TAPE_OUT` платы (в обоих режимах; раньше — MIC выбранной
  машины).

В звук идёт вход магнитофона выбранной машины (с платы или от другой машины).

## Переключатели OSD

Регистры — `SW` у `kg_mcu2` (32 по 8 бит, переключатель n = `softsw[n*8 +: 8]`, MCU шлёт их SETVAL; в link v1 был
`kg_soft_switches`). Индексы заданы полем `index` пунктов `core.json` (раньше совпадали с порядком):
0 Joystick L, 1 Joystick R, 2 Pause, 3 Reset (выбранной), 4 Reset All, 5 Frame colour (цвет рамки
выбранной машины, цвет Спектрума {G, R, B} яркий, по умолчанию 4 — зелёный), 6 NMI (выбранной),
7 + 2n DivMMC машины n (по умолчанию On), 8 + 2n SD card машины n (Real / Image, по умолчанию Image), 15 + n AY mix машины n (ABC / ACB, по
умолчанию ABC), 28 + n Sound машины n (Selected / Always, по умолчанию Selected), 19 Tape in (Board / Core, по умолчанию Board), 20 Tape out (Core 1..4, по умолчанию Core 1), 21 Keys to (Selected / All, по умолчанию Selected), 22 не используется (был Mouse middle), 23 FDD (Core 1..4, по умолчанию Core 1), 24 + n Memory size машины n (128K / 1024K, по умолчанию 128K).
Пункты машин на страницах 1..4 OSD (главная страница: «Core 1..4»); образ SD — пункт F, слот n. Значения по умолчанию
дублируются в `SW_INIT` у `kg_mcu2` в `quadspeccy.v`, чтобы ядро стартовало с ними до первой команды MCU. Новый пункт сдвигает индексы
следующих за ним пунктов, поэтому в top их надо поправить вместе с `core.json`.

Горячие клавиши пунктов разбирает прошивка MCU (`hotkey_find` в `input/input.cpp`): срабатывает первый по порядку
пункт `core.json`, у которого совпала клавиша, а пункт без модификатора совпадает при любых модификаторах. Поэтому
пункт с модификатором должен стоять раньше пункта с той же клавишей без него: «Reset All» (Menu+F12) выше «Reset»
(F12), иначе Win+F12 сбрасывает только выбранную машину (найдено на плате).
